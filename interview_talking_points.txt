==============================================
SKEETER - QUICK REFERENCE (Read Before Interview)
==============================================

ELEVATOR PITCH (30 seconds)
------------------------------------------
"SKEETER is a multiplayer party game where you play as a mosquito or a host defending human bodies. Every role is radically different. The core tension: drink more blood, get richer but slower. Do you risk one more bite, or run it home now? Last Call (final 18 seconds) is worth 2x so every round has a climax. 75 files, 13K lines of C#, peer-to-peer multiplayer, proximity voice, bot AI, and a highlight system for streamers."


THE PROBLEM & SOLUTION (2 min)
------------------------------------------
PROBLEM:
  - Party games stuck in 1v1 (nobody to root for) or huge multiplayer (can't watch)
  - No asymmetric games at 2-4 player scale
  - Streamers need climax every round, not every hour

SOLUTION:
  - Asymmetric roles (mosquito vs host) - flipped each round
  - 90-second rounds with designed climax (Last Call)
  - Visual feedback designed for clips (near-miss slow-mo, freeze-frame, vertical capture)
  - Bot AI fills empty seats
  - Proximity voice makes coordination risky


CORE LOOP (elevator pitch version)
------------------------------------------
You are a mosquito.
  - Land on human skin → automatically drink blood
  - Blood fills belly, makes you heavier (slower + no dash)
  - Carry blood to glowing window → "bank" it for points
  - Die before banking = lose everything

As a host:
  - Control 3 human bodies
  - Click to swat mosquito
  - Tab/1/2/3 to switch bodies
  - Prevent mosquito from reaching window


8 KEY FEATURES (order of importance)
------------------------------------------
1. Asymmetric multiplayer (2-4 players, roles random)
2. Tension loop (blood = heavy, creates decision every round)
3. Last Call mechanic (final 18s worth 2x points)
4. Multiplayer (LAN + WAN with port forwarding)
5. Bot AI with difficulty ladder
6. Visual feedback for clips (slow-mo, freeze-frame, vertical capture)
7. Personal best tracking
8. Accessibility (motion, colorblind, interface, danger cue)


ARCHITECTURE SUMMARY (1 min)
------------------------------------------
Code-first design:
  - No scene files, no prefabs
  - ArenaBuilder.cs constructs entire round in code
  - Enables: instant restarts, text diffs, engine ports

8 Subsystems:
  1. Core (GameEvents spine, Tuning constants, MatchDirector)
  2. Mosquito (flight, feeding, death)
  3. Human (body control, squad switching, swat)
  4. AI (perception, bot brains, difficulty)
  5. Voice (proximity audio, detection integration)
  6. Presentation (camera, shake, particles, ragdoll)
  7. Networking (peer-to-peer UDP)
  8. UI (HUD, menus, recap)

Why event-driven?
  - Audio, particles, HUD, logs all listen to same events
  - Add reaction without touching gameplay code
  - No spaghetti references

Q&A ANSWERS (30 sec each)
------------------------------------------

Q: "Why Unity?"
A: "Cross-platform (Windows/macOS/Linux/future iOS), fast to iterate with scene-free design, good audio synthesis support, low barrier to entry (C#). If rebuilding, I'd use Godot, but for 2-month sprint, Unity's ecosystem saved time."

Q: "How would you scale this?"
A: "v1 is peer-to-peer (no scaling needed). To scale: (1) Relay server (~200 LOC) for NAT traversal, (2) Leaderboard backend for ranked play, (3) S3 for replays, (4) iOS/Android ports. Key: don't need server until strangers play ranked. Friends-only stays peer-to-peer (faster, cheaper, lower latency)."

Q: "Hardest part?"
A: "Two things: (1) Asymmetric balance - took 3 weeks to dial in belly curve so 'too full to dash' happens before 'too full to fly'. (2) Audio synthesis + voice perception - mixing procedural audio with real microphone input and making bots react to it. Took 2 weeks to get sub-100ms latency and no clicks."

Q: "What would you do differently?"
A: "(1) Assembly definitions from day one - documented boundaries but didn't enforce. (2) Input system migration - legacy Input Manager works but new system is cleaner. (3) Voice transport interface first - bolted on network later, should've decoupled earlier."

Q: "Why this core loop?"
A: "Blood = weight creates visible tension. Player sees belly fill (visual indicator of risk), speed drops (mechanical consequence), and every decision is visible on the player's own body. Contrast with abstract resources (numbers on screen) that don't drive engagement."

Q: "Networking approach?"
A: "Peer-to-peer. Movement owned by whoever drives it (client-owned, no rubber-banding for your own mosquito). Outcomes (bites, banks, kills) host-authoritative so no dispute. Right trade-off for friends playing together - trusts players, low latency. If ranked comes later, switch to server-authoritative movement."

Q: "Accessibility?"
A: "Not bolted on, designed in: Reduce motion (disables slow-mo/camera punches), colorblind modes (cyan-safe colors), tap instead of hold (buzz/mic), interface scaling, danger cue (text warning for swat). Everyone can play."
